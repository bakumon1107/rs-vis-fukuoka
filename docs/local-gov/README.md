# 地方版 予算ビュー（local-gov）

国の予算可視化（本家 `team-mirai-volunteer/rs-vis`）をベースに、自治体の予算を可視化する「地方版 ○○予算ビュー」を作るための作業フォルダ。

## 方針

- **1本のコードで複数自治体に対応する**。自治体ごとの違いはデータと設定で切り替え、ブランチは分けない。
- **最初の事例は福岡県**。1件目は具体的に作り込み、2件目の自治体に着手する時点で共通化を本格的に進める。
  - ただし1件目から、自治体名・データの置き場所・金額単位などは定数や設定に集め、ハードコードを散らさない。
- 本家との差分をできるだけ小さく保ち、本家の改善を取り込み続けられるようにする。

## ブランチ運用

| ブランチ | 役割 | 更新方法 |
|---|---|---|
| `main` | 本家 `main` のミラー。直接変更しない | 本家に追従して fast-forward のみ（`gh repo sync` / `git push origin upstream/main:main`） |
| `local-main` | 地方版の本流（既定ブランチ） | 作業ブランチから PR でマージ |
| `feat/*` `fix/*` `docs/*` | 個別作業 | `local-main` から worktree で切る |

本家の取り込み: `main` を同期 → `main` → `local-main` の PR を作って衝突を解消。

リモート: `origin` = フォーク（bakumon1107/rs-vis-fukuoka）、`upstream` = 本家（team-mirai-volunteer/rs-vis）。本家への push・PR は行わない。

## このフォルダの構成

```
docs/local-gov/
  README.md   … 方針・ブランチ運用・ロードマップ（恒久的な文書）
  knowhow/    … 自治体をまたいで使える調査・作業のノウハウ（新しい発見があれば追記する）
  tasks/      … 設計・調査・計画（YYYYMMDD_HHMM_タイトル.md）
  fukuoka/    … 福岡県固有の調査（入口ページ早見表・資料の癖・調査の記録）
```

**ノウハウの蓄積ルール**: 調査や作業で分かったこと（どこに何があるか・ファイルの見分け方・落とし穴・やってみて効果がなかったこと）は、その都度 `knowhow/`（自治体共通）か `<自治体>/README.md`（自治体固有）に書き足す。同じ調査を二度しないため。

地方版の作業文書は本家の `docs/tasks/` ではなくここに置く（本家取り込み時の衝突回避と、文書の埋没を防ぐため）。

## テスト（抽出・検算ロジックの回帰を防ぐ）

抽出・OCR の解釈のロジックは、崩れ方に合わせて継ぎ足していくので、直したはずの崩れ方の再発や、別の箇所の数字の変化に気づけるようにする。

| 種類 | 場所 | 内容 | 実行 |
|---|---|---|---|
| 単体テスト | `scripts/local-gov/fukuoka-pref/tests/test_*.py` | 解釈の関数を、実際に起きた崩れ方（出典のページをコメントに書く）を再現した小さな入力で確かめる。原本不要 | `python3 -P -m pytest scripts/local-gov/fukuoka-pref/tests` |
| 回帰テスト | `scripts/local-gov/fukuoka-pref/tests/regression.py`・`expected/regression.json` | 手元の原本と OCR 結果で全ステップを流し、要約（件数・一致数・FAIL・総額）を期待値と1行ずつ比べる。原本がなければ飛ばす | `FUKUOKA_DATA=<dir> python3 -P scripts/local-gov/fukuoka-pref/tests/regression.py` |

決まり:
- ロジックを変えたら両方を流す。単体テストは新しい崩れ方を直すたびに1件足す（出典のページを書く）
- 回帰テストで数字が変わったら、良くなったのか悪くなったのかを確かめてから `--update` で期待値を書き換え、コミットの説明に理由を書く
- `<dir>` の形: `pdf/<県サイトのファイル名>.pdf`、`ocr/<名前>/p0001.json …`（`r8-ippan`・`r8-toku`）。原本はコミットしない
