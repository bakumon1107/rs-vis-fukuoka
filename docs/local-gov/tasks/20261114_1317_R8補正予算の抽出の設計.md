## 3. 説明書の形（6月補正 289925 で確認）

当初予算の説明書と同じ表で、列の意味だけが違う:

| 列 | 当初 | 補正 |
|---|---|---|
| 1〜3 | 本年度・前年度・比較 | **補正前の額・補正額・計** |
| 4〜7 | 本年度の財源内訳（国支出金・地方債・その他・一般財源） | **補正額の**財源内訳 |
| 8〜9 | 節（細節）・金額 | 節（細節）・金額（**補正額の内訳**） |
| 10 | 説明（○事項 金額） | 説明（補正で動いた事項。金額のない1事項もある「○ガス等行政費」） |

- 補正のある目だけが載る（例: 6月補正の総務費は 2款6項4目「銃砲火薬ガス等取締費」の1目だけ）。項の「計」の行は、その項の補正前・補正額・計
- テキストの説明書の文字は正確だが、`pdftotext -layout` では2行の名前（「銃砲火薬ガ／ス等取締費」）や節の折り返しが崩れる

## 4. 抽出の方式（今の部品の組み合わせ）

| 資料 | 方式 |
|---|---|
| 議案の第1表（款・項） | `extract_yosansho.py` を補正の様式に（列が「補正前の額・補正額・計」の3つ。第1条の「…を追加し、…とする」）。9月第3号の議案は文字層が崩れている（「2,31 1,3 05,1 80」）ので、第1表は OCR で読み、総括と照合する |
| 説明書（テキスト: 6月・8月専決・9月追加提案） | ページ画像に `ocr_pages.py` をかけて**表の構造（縦線・区画）だけ**を取り、`textlayer_pages.py` で各列の中身を**テキストの単語に置き換える**（当初で文字層を3つ目の読み取りに使った仕組みと同じ。テキストなので字も数字も正確）。OCR の文字は使わない |
| 説明書（画像: 9月第3号） | 当初予算と同じ（PP-OCRv6・v4 ＋ 文字層の多数決、`refill`・修正表）。44ページで OCR は1時間ほど |

`parse_setsumeisho.py` には「補正の列」の切り替え（引数）を足す。列1〜3の意味を変え、検算 C を「補正前 + 補正額 = 計」にする。
検算 A（説明欄の合計）・B（財源内訳の合計）・D（節の合計）は「= 補正額」。当初の解釈が変わらないことを回帰テストで確かめる。

## 5. 検算

補正の設計書 5章のとおり（すべて完全一致を要求）。今回の資料で使えるもの:
- 目: 補正前 + 補正額 = 計、説明欄・節・財源内訳の合計 = 補正額
- 項・款: 目の**補正額**の合計 = 議案の第1表の補正額（説明書には補正のある目だけが載るので、補正前・計は目の合計と比べない。
  議案に載らない項の目の補正額は 0）。第1表の補正前・計は、款・項の単位で回の鎖（下）と総括で確かめる。総括の合計 = 第1条の追加額
- **回の鎖**: 前の回の「計」= 次の回の「補正前の額」（目の単位まで。補正のない目は前の回のまま）、最初の回の補正前 = 当初の公開データ（目の単位）

## 6. データの持ち方

補正の設計書 3章のとおり（補正は差分。補正後は当初 + Σ補正）。公開データは:
- `budget-2026-initial.json` は変えない
- 補正ごとのファイル（例 `budget-2026-supplement-1.json` …）か、1ファイルに回の配列か → 8章の1
- 説明欄の事項の対応: 補正の事項が当初の同じ目に同じ名前であれば足し込み、なければ「補正で追加された事項」（`added_in: "R8-09-3"` のような印）

## 9. 実装の結果（2026-11-14）

- 4回とも、議案・総括の検算と、目の明細の検算（4回の計で 目 歳出 20・歳入 14 = 34目）がすべて一致。目の補正額の合計 = 総括の款の補正額。
  回の鎖（当初 → 9月追加提案の後 2,313,266,114 千円）も款・項の単位でつながる
- 実装で分かったこと:
  - 画像の説明書（9月第3号）は**減額の印 △ を OCR が読まない**（PP-OCRv6・v4 とも）。文字層に △ が単独の語であるので、同じ行・同じ欄の数字に付ける（`mark_negatives.py`）
  - 9月第3号は1200dpi の白黒2値で、罫線が細く途切れるページ（p20・p23）で列が足りなくなった。`OCR_LINE_CLOSE=25 OCR_LINE_COVERAGE=0.4` で流し直した
  - 9月第3号の議案（画像）の文字層は、金額が2語に割れる・カンマを「.」と読む・款の番号を「，」と読む。列の位置で語をつなぎ、款の番号は前の回の計で決める
  - **当初予算の「前年度にだけあった目」**（本年度が空欄・番号の印字なし。R8 の知事選挙費など10目）に、並び順で番号をこしらえていた。
    8月専決で新しく設けた「3 県議会議員補欠選挙費」と ID がぶつかったので、前年度のみの目は ID を `…-p<n>`・目の番号 null・`previous_only` にした（ユーザー決定 2026-11-14）
  - 歳入の説明欄には金額の印字されない事項（節ごとに1事項）があり、事項の合計が目の額にならないことがある（9月第3号の県土整備債）。合わない目は事項を載せない
    （同じく金額のない事項だけの歳入の目 = 総務債・教育費国庫補助金なども、事項を出さない。節は出る）
- 書き出しの後の照合（`verify_hosei.py`。回帰テストのステップ）: 目の補正前 = 当初の目の額 + それより前の回の補正額（34目）、
  項の目の合計 = 議案の項の補正額（21項）、款の財源内訳 = 総括の財源（42）。すべて一致（款の補正前の鎖は `check_hosei_chain.py`）。
  目の鎖は書き出し（`export_hosei.py`）でも見て、合わなければ FAIL（公開データの状態に反映）。入力のない回があれば、それより後の回は書き出さない
- 補正後の組み立て（`supplement.ts`）は、合計の合わない内訳を出さない: 片方にしか事項・節・財源がなく、もう片方の額が 0 でない目
  （9月第3号の歳入 7-2-3・9-2-6・14-4-6 は当初に事項がない）、入れ子の事項、負の事項。補正で新しく設けた目は同じ項の目の後ろに並べる
- 画像の議案（9月第3号）の第1条（追加額・総額）は文字層でも崩れずに読めるので、表の合計の行と照合する
- 9月第3号（画像）の読み取りの確かめ（2026-11-14）:
  - 金額: 新 OCR（v6）・旧 OCR（v4）・文字層の3つで、272 値のうち 264 が3つとも一致、8 が新旧 OCR で一致
    （文字層が繰越金の目を読めなかった分）、新 OCR だけの値は 0
  - 名前: 書き出した OCR の名前 66 件を、当初予算の名前・文字層の名前と突き合わせ、合わないものを画像で確認。誤り 6 件
    （小書き「ょ」→「よ」4、「舗」→「舖」1、細節「普通旅費」→「普通旅」1）を名前の修正表 `ocr/corrections/r8-hosei-names.json` で直す。
    節の名前の読み欠け（2行の名前の片方）は、歳出は節の番号から名前を付けるので公開データに出ない

## 8. 決めたこと（2026-11-14 ユーザー承認。どれも案のとおり）

1. 公開データの形: (a) 回ごとにファイルを分ける（当初と同じ形の行で、金額は補正額）、(b) 1ファイルに回の配列。
   **案: (a)**。画面は「当初」「補正後（最新）」を選ぶだけで、補正後は読み込んだ回を足し合わせて作る（足し合わせはドメイン側の純粋関数）
2. 画面の「補正後」は**最新の回（9月追加提案の後）まで**を足したものとし、どの回まで含むかを画面に出す（「9月補正（第4号）まで」）
3. 9月第3号の地方債補正・繰越明許費・債務負担行為は MVP では取り込まない（金額の流れの図に出ないため）
4. 補正の説明欄の事項名は、当初と同じく裏付けを取る（テキストの3回は出典 text。9月第3号は OCR の多数決＋画像で確認）
