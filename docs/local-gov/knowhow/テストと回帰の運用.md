# テストと回帰の運用（地方版）

抽出・OCR の解釈のロジックは、資料の崩れ方に合わせて継ぎ足していく。直したはずの崩れ方の再発や、別の箇所の数字の変化に気づけるよう、3種類のテストを置く。

| 種類 | 場所 | 内容 | 実行 |
|---|---|---|---|
| 単体テスト | `scripts/local-gov/<自治体>/tests/test_*.py` | 解釈の関数を、実際に起きた崩れ方（出典のページをコメントに書く）を再現した小さな入力で確かめる。原本不要 | `python3 -P -m pytest scripts/local-gov/<自治体>/tests` |
| 回帰テスト | `scripts/local-gov/<自治体>/tests/regression.py`・`expected/regression.json` | 手元の原本と OCR 結果で全ステップを流し、要約（件数・一致数・FAIL・総額）を期待値と1行ずつ比べる。原本がなければ飛ばす | `FUKUOKA_DATA=<dir> python3 -P scripts/local-gov/fukuoka-pref/tests/regression.py` |
| データの検証 | `tests/local-gov-validate.test.ts` | 書き出した正規化データ（`public/data/local-gov/*/`）の型・ID・会計の参照・行の中の合計を確かめる | `npm test`（Node.js 22） |

決まり:
- ロジックを変えたら3つとも流す。単体テストは新しい崩れ方を直すたびに1件足す（出典のページを書く）
- 回帰テストで数字が変わったら、良くなったのか悪くなったのかを確かめてから `--update` で期待値を書き換え、コミットの説明に理由を書く。
  書き換えたら、もう一度流して差分 0 を確かめる
- 原本（PDF）と OCR 結果はコミットしない。回帰テストの入力の置き方は自治体ごとの「データの作り方」（福岡県: [../fukuoka/データの作り方.md](../fukuoka/データの作り方.md)）
- 回帰テストを流している間はスクリプトを書き換えない。各ステップはその時点のファイルを読むので、途中で書き換えると、
  書きかけの版で一部のステップが動き、後ろのステップがまとめて崩れる（2026-11-06、差分 148件になった実例。ロジックの退行ではなかった）
- `npm test` は Node.js 22 で流す（Node.js 20 では既存の2件が環境のせいで失敗する。ノウハウ「自治体データ調査の手順」7章）
