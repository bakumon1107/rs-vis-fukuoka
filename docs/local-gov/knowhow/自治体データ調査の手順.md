## 2. ファイルの種類を見分ける

PDF が「テキストで取れるか」「スキャン画像か」で作業量が桁違いになる。ダウンロードしたらまず次を見る。

```bash
pdfinfo x.pdf | grep -E "Pages|Producer"     # 作成ソフト
pdfimages -list -f 2 -l 6 x.pdf              # 画像が貼られているか（ページ全面の画像ならスキャン）
pdftotext -enc UTF-8 -layout -f 2 -l 6 x.pdf - | head   # 文字が読めるか
```

| Producer の例 | 意味 | 扱い |
|---|---|---|
| Microsoft Excel / Word / PowerPoint | 元データから出力 | テキストで取れる。表の列もほぼ揃う |
| macOS Quartz PDFContext | 元データから出力（福岡県の決算事項別明細書） | テキストで取れる。**見出しの文字が重なって二重に出る**ことがあるが数値は正確 |
| iTextSharp だけ（画像あり） | スキャンした画像を束ねたもの | **OCR が必要**。付いている OCR 層は使えない品質のことが多い |
| Adobe Acrobat Paper Capture | スキャン＋Acrobat の OCR | ある程度読めるが数字が崩れる。検算が必須 |

- スキャン画像は年度によって品質が違う（福岡県: R8 は 150dpi カラー、R7 は 300dpi 白黒）。`pdfimages -list` の `x-ppi` と `color` 列で確認する。
- 画像の中身を見るときは `pdftoppm -r 110 -png -f N -l N x.pdf out` で1ページだけ PNG にする。

## 3. 予算書の構造（地方自治法の様式で共通の部分）

- 予算に関する説明書の「歳入歳出予算事項別明細書」は全国でほぼ同じ様式: **款・項（見出し）→ 目（行）→ 本年度・前年度・比較 → 財源内訳（国庫支出金・地方債・その他・一般財源）→ 節（区分・金額）→ 説明（○事項 金額）**。
- **検算の式**（福岡県で2例を確認。どちらも一致）:
  - 説明欄の事項の合計 ＝ 目の本年度額
  - 財源内訳の合計 ＝ 目の本年度額
  - 節の合計 ＝ 目の本年度額
  - 目の合計 ＝ 項（「計」行）、項の合計 ＝ 款、款の合計 ＝ 予算計上額調
  - **目の合計 ＝ 予算書の本体（議案）の第1表・別表の項の金額**。全会計の款・項が載っている。
    款の合計の照合だけでは「項の切り替わりの見落とし」（後の項の目を前の項に入れる）が素通りする（福岡県 R8 歳入で実例）ので、必ず項の単位でも照合する
- 予算書の本体（議案）は議会に出す形のもので、スキャン画像でも発行元の OCR 層が付いていることが多い。金額は単語単位なら読めることがある（福岡県 R8 は全20会計で検算一致）
- 公営企業会計（病院・下水道・電気・工業用水道など）は款項目の第1表がなく、議案の第3条（収益的収入及び支出）・第4条（資本的収入及び支出）に款・項が条文で並ぶ。
  目の単位は説明書の「予算実施計画」。福岡県 R8 では予算実施計画のページに使える文字層があった（名前の字は崩れる）
- 説明書には**担当課が書かれていない**。課は編成概要の施策別資料（課名＋款項目の番号＋事項名）や見直し一覧から補う。
- 決算の概要説明書には**部局別の款 × 項**があることが多い（部局の列はこちらから作る）。
- 単位: 予算書は千円、決算の事項別明細書は円のことがある。**取り込み時に必ず1円単位にそろえる**。
- 会計間の重複: 一般会計の「諸支出金」「公債費」と特別会計の「公債管理」「国民健康保険」などは繰出金・繰入金で重複する。

## 4. サイトの巡回

自治体サイトはカテゴリの木（福岡県なら `/life/<大>/<中>/<小>/`）でページが整理されていることが多い。
人がたどるより、カテゴリページを機械的に巡回してページのタイトルを集め、キーワードで絞るほうが早く漏れがない。

- スクリプト: `scripts/local-gov/fukuoka-pref/research/crawl_life.py`（福岡県用。BASE と URL パターンを変えれば他の自治体にも使える）
- 先に `robots.txt` を確認する。間隔は1秒に1件以上空ける。
- 絞り込みのキーワード例: 補助・交付・助成・採択・交付決定・交付対象・実績・公表・委託・契約・指定管理

## 5. テキスト PDF の表を抽出するときの落とし穴（福岡県 R6 決算で実際に起きたもの）

`pdftotext -layout` の出力を行単位で読む方式で、次の癖に対応した（`scripts/local-gov/fukuoka-pref/kessan_common.py`）。

| 癖 | 例 | 対応 |
|---|---|---|
| 長い名称の折り返し（4形式） | A: 上の行／「1資金貸付事業 数値」／下の行、B: 上の行／「2」／「特別会計繰入金 数値」、C: 上の行／「1」／下の行／数値だけの行、D: 上の行／「6 事務費」／数値だけの行 | 番号の位置より深く字下げされた断片だけを名前に使う。**ページをまたぐ折り返し**もあるので、ページ単位でなく区間（部局・項）単位の行の流れで解釈する |
| 過誤納金（内数） | 収入済額が次の行に単独で出て、上の行に「(1,046,800)」 | 次の行の数値を収入済額の列に戻す。調定額 = 収入済額 − 過誤納金 + 不納欠損額 + 収入未済額 |
| 右端の備考欄 | 「67,539,819　予備費補充　3,285,777 円」 | 最後の数値の後ろを備考として切り離す。**非貪欲マッチにすると行頭の番号の直後で切ってしまう**（実例あり） |
| 列構成の違う表 | 予備費だけ「当初予算額／補正予算額／予備費支出及び流用増減額／計／支出済額／不用額」の6列 | 款番号で分岐 |
| 字下げの揺れ | 款 0-1 / 項 4-5 / 目 8-9 文字（ページで1文字ずれる） | 固定しきい値で段を判定 |
| 全角数字 | Python の `\d` は全角数字にも一致する。目次の「教育庁……186」の直後の章番号「７」を巻き込んで 1867 になった | ページ番号などは `[0-9]` で書く |
| 目次が2ページにまたがる | R6 決算概要説明書の目次は PDF 3〜4ページ | 先頭数ページをつなげて読む |
| 文字コードのない文字 | 事項別明細書で一部の漢字が `(cid:3222)`（フォントに ToUnicode がない） | 数値は正しく取れる。名称は別の資料（概要説明書）から取る。Adobe-Japan1 のフォントなら poppler の `UniJIS-UTF32-H` を反転して CID→Unicode に戻せる |

**福岡県 R6「歳入歳出決算事項別明細書」（272615.pdf）の構造メモ（未抽出・次の作業）**:
- 文字が**2回ずつ描かれている**（位置が少しずれた2層）。pdftotext では「1 報酬 1 報酬 550000 550000 472100 0 0 0 77900」のように名前と金額が二重に出る
- 節の行: 区分 / 節の金額 / 支出済額 / 翌年度繰越額（継続費逓次繰越・繰越明許費・事故繰越し）/ 不用額。**節の金額 − 支出済額 − 繰越額 = 不用額** で二重分の除去を検算できる
- 目の行には予算現額の内訳（当初予算額・補正予算額・継続費及び繰越事業費繰越額・予備費支出及び流用増減額・計）が付く
- 目の名称の一部が文字コードなし（`(cid:N)`）。目は予算現額・支出済額で款項目別明細表（概要説明書）と照合して特定し、名称はそちらから取る
- **2層で描かれていないページもある**（p55・p156）。2層の判定はページ全体ではなく節の金額の列の数字で行う（ページの他の場所には1層のページにも同じ色の型の文字がある）。
  判定を誤ると、その列が全行読めずに節を行ごと捨て、目が対応しなくなる（4目が対応しなかった原因）
- 単位は円。節の内訳は「性質」（人件費・委託料・負担金補助及び交付金…）の決算として価値がある

**検証の考え方**: 合計の検証（縦・横・合計行）だけでは**名前の取り違えは検出できない**。
名前は、同じ書類の別の箇所（例: 款項目別明細表と部局別の表）から独立に取って一致を確かめる。
実際に、名前に数字が混ざる誤りを合計の検証は素通りしていた。

## 6. スキャン画像の表を OCR するとき（福岡県 R8 予算説明書で検証）

スクリプト: `scripts/local-gov/fukuoka-pref/ocr/ocr_pages.py`（OCR して保存）→ `parse_setsumeisho.py`（表の解釈と検算）

- **OCR エンジン**: RapidOCR（PaddleOCR のモデルを onnxruntime で動かす。pip で入る。システムのパッケージ不要）。
  **`rapidocr`（3.x）の PP-OCRv6 small・日本語（`Rec.lang_type=japan`）を使う**。`pip install --target <dir> rapidocr`。モデルは初回に自動で取得される。
  - 最初に使った `rapidocr_onnxruntime`（1.4）には中国語モデルしかない。数字は正確だが、**日本の字形（総・繰・譲・災・県 など）を持たず、黙って落とすか簡体字に置き換える**（「総務費」→「務費」、「繰入金」→「入金」、「県民税」→「民税」）。金額の検算では見つからず、名称を R6 決算の目名と突き合わせて初めて分かった
  - 比較（3ページの款項見出しと目名の列）: v4 中国語は字が抜ける／v4 日本語は余計な文字が混ざる（「1丁般管理費」）／v5 server は正確だが 7倍遅い／**v6 small 日本語は正確で旧モデルより速い**／v6 medium は正確だが 14倍遅い
  - v6 は数字の途中に空白を入れることがある（「17,854, 435」）。金額を読むときは空白を除く
  - 新しいモデルでも「减債」のように簡体字が少し残る。名称は別資料との照合（下記）で確かめる
- **列ごとに切り出して OCR する**。ページ全体を一度に読むと、隣の列の文字がつながって1つの文字列になる（「2,444管理事務费」）。
- **罫線の検出**: OpenCV のモルフォロジー（縦長・横長の構造要素で開く）。
  - 罫線＝表の高さの半分以上にわたる縦線。列見出しの中の短い線を罫線と取り違えると列の境界がずれ、**右寄せの数字の末尾が欠ける**（「2,947,24」）
  - 1ページに複数の表がある（項がページ途中で変わる）。縦線が途切れる高さで表を分ける
  - **縦線は表ごとにも検出する**。特別会計の小さな会計では1ページに歳入（7列）と歳出（11列）の短い表が並び、ページ共通の縦線では列がずれる・短い表の線が基準に届かない。
    表ごとに「表の下端まで届く縦線」を数え、ページ共通の本数以上のときだけそれを使う（長い表では行の区切りで縦線が途切れ、表ごとの基準だと本数が減るため）
  - 目の区切り＝表の幅いっぱいの横線
- **速度**: RapidOCR の既定（`det_limit_type=min`、短い辺を 736px まで拡大）だと、細長い列の切り出しが数倍に引き伸ばされて**1ページ 35 秒**かかった。
  `det_limit_type="max", det_limit_side_len=2400, use_cls=False` で **約 10 秒**に（数字の読み取り結果は同じ）。
  並列実行するときは `intra_op_num_threads` を絞る（絞らないと onnxruntime が全コアを取り合い、4並列で1ページ 170 秒に悪化した）。
- **解像度**: 300dpi で描画。200dpi でも数字はほぼ読めたが、正確さ優先で 300dpi にした。
- **検算で正しさを担保する**（目ごと）: 説明欄の合計 = 本年度、財源内訳の合計 = 本年度、|本年度 − 前年度| = |比較|、節の合計 = 本年度。
  さらに款の合計を、テキスト PDF の計上額調と照合する。**R8 福岡県一般会計で全29款が千円単位まで一致するところまで到達**。

予算説明書の書き方の決まり（検算の前提として知っておくこと。福岡県 R8 で確認）:

| 決まり | 例 | 扱い |
|---|---|---|
| 列見出しのない続きのページ | 目がページをまたぐと、次のページは列見出しなしで節の続きから始まる | 見出し語の有無で判定し、上端から本文として読む |
| 説明欄の入れ子 | 親「○中小企業振興資金融資費 214,794,000」の下に字下げした内訳 | 書き出し位置で親子を分け、親だけで照合 |
| 説明欄が1事項だと金額を省く | 「○病院事業会計への負担金」（金額なし） | 目の額を当て、照合済みではない印を付ける |
| 説明欄の注記（金額なし） | 「○事業費支弁職員 2人」の下に「○漁港修築事業費」（p292）、「○県営住宅課所管」だけ（p407）、「○職員費 11,264人」（p365） | 人数の注記・所管の注記は事項にしない。名前末尾の「N人」は人数として分ける（画像で確認） |
| 目番号は年度で変わる | R6 の 2款1項3目は「広報費」、R8 では「文書費」 | 年度をまたぐ照合は番号でなく名前で |
| 名前が2行の目 | 目番号は2行の間の高さに単独で印字される | 番号を外してから行にまとめる（番号ごとまとめると「指導費生活衛生」と前後が入れ替わる） |
| 特別会計の区切り | 会計ごとに「○○特別会計歳入歳出予算事項別明細書 1 総括」で始まり、給与費明細書・地方債の調書で終わる | 見出しで会計を進め、計上額調の会計の並び順で名前を当てる（OCR の会計名は崩れる）。給与費明細書以降は次の会計まで読み飛ばす |
| 公営企業会計 | 「予算実施計画」（収益的収入及支出・資本的収入及支出）＋キャッシュフロー計算書・貸借対照表。款項目の様式ではない | 別の解釈が必要 |
| 説明欄が空の目 | 税交付金・公債費の元金など | A は対象外 |
| 本年度 1 千円の科目 | 証紙収入・繰越金・利子割精算金 | 小さな「1」は文字検出が落とす → セルを拡大・二値化して読み直す |
| 本年度の計上がない目 | 知事選挙費（前年度だけある） | 「比較 = 前年度」のときだけ本年度 0 とみなす |
| 節と細節 | 細節は内側の枠で字下げ（列の左端から 30px 以上） | 番号の有無でなく字下げで区別。歳入の節は 45〜52px に印字され細節はほぼない |

OCR の落とし穴（追加）:
- 1ページに縦線の欠けた表が2つあるとき、1つ目の補正でページ全体の縦線の一覧を書き換えると2つ目を読み飛ばす（実例: 生活労働費が 218,831 千円ずれた）。補正は表ごとに
- 数字の 1・0 が英字（l, I, O）で返ることがある。数字の文脈でだけ置き換え、検算で確かめる
- かすれた「1」は「一」「二」と読まれる。大津の二値化をしてから読むと「1」になった

**OCR だけで解決しようとしない**（福岡県 R8 一般会計を 100% にした方法）:
- スキャン画像の PDF でも、発行元が付けた文字層（OCR 層）があることが多い。単独では質が低い（全検算一致 28%）が、**OCR とは読み違いの癖が違う2つ目の読み取り**になる
  - `ocr/textlayer_pages.py` で OCR と同じ表の構造（縦線・区画）に流し込み、同じ解釈スクリプトにかけて目ごとに比べる（`ocr/cross_check.py`）
  - OCR で検算が通らない目は、値の組（本年度・前年度・比較／財源内訳／節／説明欄）を文字層の値に差し替えて全検算が通るか試す。
    節は1件ずつ（OCR の取りこぼし・細節の誤認・重複と、文字層の誤読が同じ目に混ざる）。**最小の変更で1通りに決まるときだけ**採用し、出典を記録する
  - 結果（最初の版）: 中国語モデルの OCR だけで 369目、文字層との組み合わせで 14目、残り1目（4件）は画像で確かめて修正表に記録 → 383/383。
    ただしこの中に打ち消し合う誤りが2目あった（次の項目）
  - 結果（2026-11-06 改訂）: PP-OCRv6＋セルの拡大読み直し＋修正表（画像で確認した7件）で 381目、節と細節の取り違えの2目を文字層との突き合わせで直して 383/383。
    全検算一致の目の値 6,344件の 99.9% が2通り以上の読み取りで同じ値、残り5件はすべて画像で確認済み
- **検算の式は「打ち消し合う誤り」を通してしまう**。R8 p239 の財源内訳で、文字層は「その他」の 1 を取りこぼし、同時に一般財源を 34,763 → 34,764 と誤読していた。
  組ごと文字層に差し替えると合計が目の額に合い、検算を通った（画像で発見）。対策（`ocr/cross_check.py`）:
  - 財源内訳は区分ごと・**断片ごと**に突き合わせる（「その他」は「使用料及び手数料 24／財産収入 1／諸収入 142,841」のように複数の金額の合計）。
    取りこぼした断片を別の読み取りから**足す**のはよい（読めなかったことは別の値の証拠にならない）
  - **2つの OCR が同じ値を読んだ箇所は固定**し、文字層で書き換えない（`--third` に別の OCR を渡す）
  - 多数決（`ocr/vote.py`）で裏付けが1通りだけの値を洗い出し、画像で確かめて修正表に書く
- **文字層の座標は画像とずれる**（R8 281298 は右に 10〜23px。ページで違う）。境目の近くの右寄せの「1」が隣の列に入る。
  OCR と同じ文字列の数字（4文字以上）でページごとのずれを測り、**数字だけ**戻す（名前まで戻すと字下げで見分ける細節がすべて節になった）
- 小さな「1」は新旧どちらの OCR も取りこぼす（同じ弱点を持つので多数決では救えない）。`ocr/refill_missing.py` のセルの拡大・二値化で読める。
  R8 一般会計では読み直しだけで歳入が全151目一致になった
- PP-OCRv6 特有の崩れ: ページ番号「-138-」の末尾を「一」と読む（項の名前と誤認）、項の見出しを「狩10項」と名前が1文字だけ前に出る
- **同じページに歳入（7列）と歳出（11列）の表がある**と、縦線の本数だけでは見分けられない（歳出の表でも途切れた線で8本になる）。
  列見出しの語（「財源」「国庫支出金」「一般財源」があれば歳出）で見分け、見出しのない続きの表は直前の表の種類に合わせる
  （`ocr_pages.choose_vlines`。R8 特別会計 p9・p45・p51 で実例。一般会計は該当ページなし）
- 特別会計の会計の頭の「1 総括」の表（款ごとの本年度・前年度）を目として読むと二重に数える。款の見出しが出る前の表は読まない
- 節の欄がもともと空の目（予備費）をセルの拡大で読み直すと、ないはずの「1」を拾う。読み直しは「区分の文字があるのに金額が読めない」ときだけ
- 文字層の数字の断片は重なっていることがある（「411,」と「141」が約1pt 重なる。281299）。隙間がマイナスでもつなぐ
- 結果（R8 特別会計 14会計）: 新 OCR＋読み直し＋修正表（画像で確認した10件）で 112/112 目が全検算一致、項 83/83、計上額調 28/28
- 他の照合先: 予算書の本体の項の金額（項の振り分けの誤り）、前年度の説明書の本年度（R8 の前年度列の確認。未実施）、施策別資料の事項の予算額
- 検算の式で1つだけ欠けた値は逆算できるが、それは「推定」。画像か別の読み取りで裏付けが取れたときだけ採用する
- 手で直す値は修正表に「ページ・目・列・値・根拠」を書き、修正後も全検算を通すことを条件にする

名称の確かめ方（`ocr/check_names.py`）:
- 款名: 同じ年度の計上額調（テキスト）と款番号で照合
- 目名: 前々年度の決算の款項目別明細表（テキスト）の、同じ款の目の中で最も近い名前（番号では引かない）
- 説明欄の事項名: 同じ年度の施策別資料（テキスト）の事項は科目（款 項 目）と予算額を持つので、科目＋金額で対応を取る。
  ただし**施策別資料の事項名は説明書の事項名と言い回しが違うことがある**（説明書「電子県庁管理費」＝施策別資料「県庁基幹系システム再構築費」、同じ金額）。名前の近いものだけを補正に使う
- 施策別資料の科目は「2」だけのように欠けることがある（抽出の限界）。前方一致で引く

## 7. 作業環境の落とし穴

- `npm test` は **Node.js 22** で流す（`PATH=$HOME/.nvm/versions/node/v22.21.1/bin:$PATH npm test`）。既定の Node.js 20 だと、
  `Object.groupBy` を使うテストと Supabase の WebSocket を使うテストの2件が失敗する（コードの不具合ではない。2026-11-06 確認）
- メインのディレクトリ（`rs-vis-fukuoka`）には `node_modules` がない。画面・テストの作業をする worktree でだけ `npm ci` する

- `pdftotext` は `-enc UTF-8` を付ける（付けないと Python で読むときに文字コードエラーになるファイルがあった）。
- Python は `python3 -P` で実行する（スクリプトのディレクトリを import パスに入れない）。`-I` だとユーザー領域（`~/.local`）のパッケージが無効になり、入っている `pdfplumber`・`openpyxl`・`pypdf`・`fontTools`・`onnxruntime` が使えない。
- `python3 -m venv` は ensurepip がなく失敗する。追加のパッケージは `pip install --target <スクラッチ>/pylib ...` で入れて `sys.path` に足す（OCR 用の `rapidocr-onnxruntime`・`opencv-python-headless` はこれで入れた）。
- **原本（PDF・Excel）と、そこから丸ごと書き写したデータはコミットしない**。抽出・OCR の中間結果はスクラッチ（リポジトリの外）に置く。
  コミットするのは、スクリプト・私たちが書いた文書・修正表と、画面が読む公開用の正規化データ（`public/data/local-gov/<自治体>/`。
  検算済みの数字と出典の印を持つ、共通 JSON 形式の設計 4章）。グラフはファイルにせず画面で組み立てる
- Excel（.xlsx）の中身を急いで見るだけなら `unzip -p x.xlsx xl/sharedStrings.xml`（文字列）と `xl/workbook.xml`（シート名）で足りる。
- `curl` は `--fail` を付ける（付けないとエラーページを .pdf として保存してしまう）。
- WebFetch は PDF の中身を読まない。ページの一覧取得に使い、PDF は必ずダウンロードして確認する。
- ダウンロードしたファイルはリポジトリに入れない（スクラッチ領域に置く）。URL と取得日を文書に残す。
